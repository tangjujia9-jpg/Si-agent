# Si-agent 长任务上下文与开发工具设计

日期：2026-10-22。本文定义下一阶段的实现和验收边界。
本轮已启动项目、验证更长输入并调整本机窗口配置；下文的摘要、预算结算和新工具属于待实现方案。

A 阶段的实际交付和验证见[长任务接续验收](copilot-context-continuity-release.md)。下节保留方案制定时的基线，后续工具部分仍为目标设计。

## 1. 目标与现状

Si-agent 应能连续完成“理解项目 → 制定步骤 → 修改文件 → 执行测试 → 检查差异 → 汇报结果”。
长任务依赖可接续的工作状态、可回读的原文和准确的预算，而不是不断扩大 prompt。
Si Memory 继续作为独立服务，开发工具和会话压缩都不能与长期记忆存储耦合。

当前实现存在以下限制：

| 当前行为 | 实际影响 | 代码入口 |
|---|---|---|
| 发起任务时只取最近 12 条 user/assistant 消息 | 更早的约束可能尚未超窗就不再进入请求 | `waku/server/runs.py` |
| 同一 Run 保存完整工具交互 | 文件、检索结果和错误日志会随工具轮数增长 | `waku/runtime/runner.py` |
| 输入按 JSON UTF-8 字节上界估算 | 中文、代码和重复上下文的预留可能明显大于接口报告的用量 | `waku/providers/adapters.py` |
| 每次调用先扣输入估算与输出上限，成功后尚不结算差额 | 累计预算可能较早耗尽，不能通过扩大单次窗口解决 | `Runtime._reserve` |
| 超限后移除旧回合、省略旧工具正文、缩减证据 | 原始记录仍在数据库，但发给模型的请求没有语义接续摘要 | `waku/runtime/context_budget.py` |
| 模型每次输出上限固定为 1,024 | 复杂答案、工具参数或模型内部推理可能因输出上限截断 | `waku/runtime/runner.py` |
| 工具只有记忆操作和文件读取 | 能分析项目，还不能完成修改与验证 | `waku/tools/executor.py` |

当前 UI 的累计任务预算为 64,000，API 默认值为 16,000、上限为 100,000。
它们与 Provider 的单次上下文窗口是三个不同的配置入口。
API 还限制 8 个工具名、最多 30 次工具调用；扩展工具时必须同步服务端、前端与运行契约。

## 2. 本轮实测与配置

本机继续使用 hy3，经已有 workbuddy2api 隧道访问。Jev 保持关闭。
探测只发送生成的英文记录与三个校验标记，没有发送项目资料，也没有调用 Embedding。

| 探测 | 输入正文 UTF-8 字节 | 接口报告输入 token | 输出上限 | 结果 | 耗时 |
|---|---:|---:|---:|---|---:|
| 初次小输出探测 | 53,356 | 13,055 | 128 | `length`，未完成标记回答 | 10.0 秒 |
| 调整输出后 | 53,356 | 13,055 | 2,048 | 正常结束，三个标记均找回 | 9.1 秒 |
| 更长输入 | 159,471 | 38,936 | 2,048 | 正常结束，三个标记均找回 | 9.7 秒 |

最大探测输入的本地估算为 161,927，明显大于接口报告的 38,936。
这说明当前字节上界较保守，不能把它当作实际收费 token。
标记测试只能证明这两种输入被链路接受且可回取三个位置，不代表复杂任务质量、最大窗口或账单准确性。
`/v1/models` 尚未提供实际窗口上限；本轮不据此宣称 hy3 支持 128K 或更多。

本机 `SI_COMPATIBLE_CONTEXT_WINDOW` 已从 32,768 调整为 65,536，并重启 API 和 Worker。
`/api/models` 已返回 65,536。这个值是本地运行上限，真实请求仍受网关与模型能力限制。
通用示例配置保持保守，不能把本机的探测结果推广到其他模型。

## 3. 参考现有方案后的选择

| 参考实现 | 已核对的机制 | Si-agent 的采用方式 |
|---|---|---|
| pi compaction | 预留窗口、保留最近交互、增量结构化摘要、持久化切分边界；工具批次完成后检查 | 自研相同职责的 Session Compactor，保持 Provider 无关 |
| Anthropic context engineering | 压缩历史、保留决策与未解决问题、结构化任务笔记、按需加载原文 | 任务状态单独保存，工具结果使用证据和原文指针 |
| LangChain 短期记忆 | 按 token 触发摘要，保留最近消息，使用 checkpoint 接续；工具调用与结果必须成对 | 采用状态和摘要模式，不为此替换 Si Loop |

Prompt caching 可以降低部分重复前缀的成本与延迟，但通常仍占模型窗口。
长期记忆抽取筛选的是未来可复用的事实，也不能代替当前任务的过程压缩。
首版不依赖模型厂商专用压缩 API，避免换 Provider 后无法接续。

## 4. 上下文：保留状态、压缩过程、回读原文

### 4.1 区分三类数据

1. **原始历史**：消息、工具调用、结果、审批与事件保持可审计，保存在 PostgreSQL 和受控结果存储。
2. **工作上下文**：本次目标、限制、任务状态、过程摘要、最近完整交互、当前有效证据组成模型请求。
3. **长期记忆**：稳定事实、项目决策等继续经过候选、证据、冲突和留存流程，交给 Si Memory。

过程摘要是派生的工作资料，不自动注册为正式记忆，也不能成为自证来源。
批准操作、完成测试、文件写入是否成功，均以执行器的持久化结果为准。

### 4.2 请求组装

```text
用户输入 / 上一批工具已完成
  → 读取会话摘要与最近完整交互
  → 校验任务状态、原文版本、遗忘与失效依赖
  → 获取或复用本次有效检索证据
  → 选择已授权的工具集合
  → 估算模型实际输入 + 输出预留 + 余量
  → 接近阈值？增量压缩较早的完整交互段
  → 组装工作摘要 + 最近交互 + 证据
  → 核对单次窗口与累计任务预算
  → 流式模型调用
  → 执行工具 / 审批暂停 / 完成回答
  → 保存状态，下一步重复检查
```

跨用户回合和同一 ReAct Run 都使用这条路径。
跨回合不再固定丢弃第 13 条之前的消息；加载有效摘要，再按 token 预算读取连续的历史尾部。
同一 Run 内的长期检索仍优先复用，不因压缩而每轮重做 Embedding。
模型遇到信息缺口时，可以补查记忆、文件或持久化工具结果。

### 4.3 必须保留的任务状态

`run.context` 中单独保存结构化工作状态，checkpoint 覆盖它的每次变更：

- 当前目标、用户明确约束、验收条件与尚未回答的问题。
- 计划步骤及其待办、进行中、已完成、失败状态。
- 操作 ID、真实审批状态、已完成副作用和未确定结果。
- 修改文件及版本哈希、当前失败测试、关键错误位置和原文结果 ID。
- 当前有效记忆来源、内容版本与证据 ID。

用户原始约束保留消息定位与必要的原句；不能只依赖模型多次转述。
工具完成状态由执行器更新，摘要模型无权将 `unknown` 改成成功或批准后续动作。

### 4.4 过程摘要与触发点

设模型窗口为 C，输出预留为 O，协议与估算余量为 M，可用输入为 E = C − O − M。
初始建议在输入达到 E 的 70% 时触发，压缩到 E 的约 50%；阈值须经评测调整。
这两个百分比均为配置目标，不能覆盖必须保留的约束和最新工具交换。

64K 配置的起始建议为：普通回答预留 2K 输出，复杂开发调用允许 4K，余量至少 4K。
摘要目标为 2–4K，最近交互目标约 12–16K，证据与工具 schema 单独计入。
若硬性保留内容已经超窗，不能声称可以无损压缩任意输入。

压缩发生在新请求之前、完整工具批次落盘之后。它是下一次模型调用的前置步骤，不能用过期摘要并发推进同一状态。
原始事件持久化与长期记忆抽取仍按现有异步任务流程运行。
摘要请求关闭业务工具，输入只包含上次摘要及新覆盖的历史段；超大历史分段处理。

摘要保留目标、约束、决策与依据、已做工作、未决问题、下一步、来源定位。
较长日志先使用确定性结构保存退出码、测试汇总、错误位置，再对必要的叙述做模型摘要。
相同来源与版本的重复正文可以复用引用；错误日志、最新结果和关键约束不能被相似度误判去重。

首版继续使用已配置的 hy3 生成摘要，不增加 Jev，不静默把项目数据发送给另一家服务。
摘要自身的输入、输出、延迟与失败也进入调用预算和 trace。

### 4.5 摘要持久化与遗忘

新增 `context_summaries` 保存作用域、覆盖消息/事件范围、保留边界、摘要结构、
输入哈希、来源版本、策略/提示词版本、生成模型、token 用量与状态。
每次提交都校验当前会话版本及来源版本，拒绝重复或过期摘要覆盖新状态。
原始消息和工具结果不会因提交摘要而被删除。

每次组装前重新检查摘要的证据依赖。来源修正、撤回或忘记后，相关摘要必须失效并从剩余有效资料重建。
摘要不得从已遗忘的旧文本或旧摘要中恢复内容；暂时无法重建时明确报告缺口。
多次压缩保留覆盖边界及来源定位，避免对整段历史反复做摘要，也避免只保留没有依据的“摘要的摘要”。

引用与操作 ID 可以程序化核验；摘要语义是否遗漏或曲解仍需固定样本和 judge/人工评测。
程序校验通过不等于摘要完全无损。

### 4.6 工具结果按需回读

新增受项目作用域限制的结果资源。小型结果保存在 PostgreSQL；大结果正文可保存在配置的后台 artifact 目录，数据库记录定位、哈希和大小。
存储目录不属于 Agent 可自由修改的项目目录，模型只通过 operation/resource ID 访问。
输出在保存和展示前进行脱敏；不能承诺仅靠模式匹配识别所有敏感信息。

进入工作上下文的结果包含状态、退出码、关键统计、必要错误片段、资源 ID 与分页信息。
`read_operation_result` 按 offset/limit 读取更多正文；模型不能提交任意磁盘路径。
最新完整调用与结果保持配对，旧的调用交换只有在安全边界才替换为摘要。

### 4.7 预算估算与结算

单次窗口控制上下文容量；累计预算控制整项任务的资源消耗；输出上限控制单次回答。
三者独立显示，不能再让“可继续执行的任务”因为保守预留长期累积而过早耗尽。

新增按调用 attempt 记录的预算账本，至少区分：

- 调用前的预留 `reserved`。
- 接口报告的输入/输出用量 `reported_usage`。
- 确认调用完成后的已结算用量 `settled`。
- 断线、超时、进程崩溃后的不确定预留 `uncertain`。

成功调用在事务中结算并释放差额，使用 attempt ID 防止重复结算。
已完成调用可以确认用量时，以对应 usage 替换预留；缺失 usage 或结果不确定时保留保守额度，不能直接返还。
失败后的重新调用仍是新的 attempt，不能把失败调用一律视为免费。
价格未知时只展示用量和预留，不伪造美元成本。

输入计数优先使用明确匹配模型的 tokenizer 或 Provider 计数接口。
hy3 尚无匹配计数器；首版保留字节上界作为硬回退，另用多类真实请求校准保守估算。
不能直接假定 tiktoken 等同 hy3 tokenizer，也不能依据本轮两个英文样本对所有中文、图片、工具 schema 统一除以四。
估算记录来源和安全余量，汇报中区分应用估算、网关报告和账单。

建议开发任务预设为：累计预算 256K、最多 20 次模型迭代、40 次工具调用、600 秒活动期限。
它们属于待实现预设，需同步 API 上限；普通问答继续使用较小预算。
长命令使用独立 job 和截止时间，人工审批等待采用可恢复状态，不能无限延长活动执行时间。
达到预算时保存进度、文件差异和未决步骤，支持用户继续，不能自动无限扩额。

### 4.8 失败恢复

摘要失败时不覆盖有效摘要、不执行新副作用。可以重试一次，仍失败则保存 checkpoint，报告可恢复的压缩失败。
正常路径不再静默降级成移除关键历史。确定性结果折叠仍可在保留任务状态和原文定位的前提下使用。
Provider 明确拒绝长度时，在未发布回答且不重放工具的条件下，降低有效窗口、压缩并有界重试。
输出达到 `length` 时单独判断回答未完成；不能当成输入超窗，也不能执行不完整工具参数。

新增 `context_estimate`、`compaction_start/end`、`usage_settled` 和恢复事件。
聊天中只显示“整理上下文”“继续执行”等进度；监控中展示压缩覆盖范围、前后大小、用量来源和失败原因。
用户可以查看摘要与原文定位，但产品不展示或要求模型的隐藏推理过程。

## 5. 工具：完成开发任务闭环

### 5.1 当前八个工具

| 工具 | 当前作用 |
|---|---|
| `search_memory` / `read_memory` | 读取项目内的有效证据与原文 |
| `propose_memory` / `change_memory` / `forget_memory` | 提议记忆、修正/撤回、按明确要求忘记，保留审批与生命周期检查 |
| `list_project_files` / `read_project_file` / `search_project_files` | 读取关联目录或导入快照，当前不修改磁盘 |

首批新增九项能力后共有 17 项注册工具；同一次模型请求只暴露当前模式已授权的集合。
这不是完成度指标，是否能完成真实任务才是验收标准。

### 5.2 首批工具

| 工具 | 能完成的工作 | 关键约束 |
|---|---|---|
| `apply_project_patch` | 新建或修改代码、测试、文档，返回预览与应用结果 | 审批绑定具体 diff、根目录和预期文件哈希 |
| `run_project_command` | 执行测试、构建、lint、脚本与诊断命令 | 结构化 argv、执行环境、超时、输出资源、审批策略 |
| `get_command_result` | 获取执行进度、退出码、日志片段与生成文件清单 | 持久化 job ID；轮询不能重复启动进程 |
| `stop_project_command` | 停止本次任务创建的命令和子进程 | 验证命令归属，停止结果可能需要检查 |
| `git_status` | 检查已有修改与新增文件 | 不自动覆盖用户修改 |
| `git_diff` | 检查具体补丁与文件差异 | 分页、大小限制；禁用外部 diff/textconv 执行 |
| `git_log` | 理解最近提交、变更原因和文件历史 | 有界读取；处理不可信仓库配置 |
| `update_plan` | 维护步骤、进度、阻塞与下一步 | 不能伪造文件修改、测试成功或审批状态 |
| `read_operation_result` | 回读较早工具输出、错误日志和结果片段 | 项目作用域、结果版本、分页和遗忘检查 |

现有文件工具同时增加目录/glob 过滤、命中分页和更明确的扫描覆盖率。
目前文件清单最多 500 项，搜索只是字面匹配；工具必须说明扫描范围，不能把不完整扫描说成全项目无结果。
按路径允许必要的 `.gitignore`、`.github/workflows` 等项目配置，继续限制密钥与运行数据。

网络检索与网页读取排在第二批：`search_web` 走明确配置的服务或 MCP，`fetch_url` 处理重定向、大小、超时及内网访问限制。
搜索返回来源 URL 和抓取时间，不自动把网页内容写成长期事实。
PDF、Office 解析和浏览器交互根据实际任务按可选依赖扩展；不一次性把所有工具 schema 发给模型。
Git 提交和推送作为后续独立动作，具备明确的内容/远程预览和授权后再开放。

### 5.3 模式和权限

前端提供“分析”“开发”模式；项目在服务端分别配置读文件、改文件、运行程序和联网能力。
模式选择只是请求，服务端始终按项目授权求交集；模型不能调用工具给自己增加权限。
纯导入快照可以分析和生成补丁 artifact，只有明确关联的可写工作区才能应用到磁盘。

工具目录通过统一 registry 生成 API 支持集合、模型 schema 和 UI 名称，避免三个硬编码清单不同步。
`ToolSpec` 扩展效果类型与执行策略，区分只读、文件变更、进程、联网和远程动作。
记忆修改继续执行原有证据、候选、版本与审批流程，不能因为进入开发模式绕过。

### 5.4 文件变更的可靠性

服务器解析相对路径，拒绝根目录逃逸、符号链接/junction 绕过、敏感文件及未授权根目录。
审批后再次校验目标与文件哈希，拒绝使用已经过期的预览覆盖新修改。
禁止默认整文件盲写；补丁必须能匹配明确的旧内容或新建前置条件。

每个文件使用临时写入与原子替换，多文件操作使用持久化 journal 记录完成与待完成项。
多次原子替换不等于跨文件事务；中途失败返回 `partial`，必要时按原哈希执行可检查的补偿。
重复 operation ID 返回已有结果，不能重复应用补丁；前后哈希用于核对已经发生的写入。
初版不开放批量删除、目录搬移或自动回滚整棵工作区。

### 5.5 命令执行环境

只限制 `cwd`、使用 argv 或配置命令白名单，都不等于安全沙箱。
即使是 `pytest` 和 `npm test`，项目代码也可能访问宿主机文件、环境与网络。

默认开发执行器采用容器中的项目快照或隔离工作副本，只挂载明确需要的数据，
不注入模型密钥、SSH agent、宿主 home 或 Docker socket；网络按任务配置，进程和资源有界。
命令结果标注被测试的快照/文件哈希；容器内生成的任意修改不能自动回写真实工作区。
需要保留的产物经过资源导出或受控补丁流程，避免测试命令绕过文件审批。

Windows/WSL 的本机执行保留为显式开启的可信开发模式，界面说明其宿主权限。
容器不可用时不能静默降级为本机执行，应显示环境未就绪或使用已明确配置的可信模式。
依赖安装和联网单独授权；不让后台自动执行不可信项目的安装脚本。

命令通过持久化 job 运行，流式展示进度，模型通过 ID 查询。
Windows 使用 Job Object，Linux 使用进程组或容器级限制管理子进程、超时与取消。
不能仅凭可复用的 OS PID 认领任务；进程归属绑定 job/执行环境和创建标识。
中断后先检查既有进程与结果，无法确认的操作标为 `unknown`，不自动重放。

### 5.6 结果、审批与可观测性

继续使用结构化 ToolResult、operation ID、outbox、幂等与 checkpoint。
Outbox 保证请求可持久交付，但不能单独保证外部动作“恰好执行一次”。
所有审批绑定动作、参数、资源版本和预览哈希；模型自己给出的“已批准”文本没有效力。
用户在对话中看到修改预览、执行状态、测试摘要、差异与最终产物位置。
完整日志、重试、预算、partial/unknown 和性能细节留在独立监控中，并预留 Langfuse 映射。

## 6. 实现顺序与验收

### A：上下文先行

先交付模型输入计数策略、预算账本结算、动态输出额度、结构化任务状态、增量会话摘要和原文回读。
替换固定 12 条历史的接续方式，再将旧请求省略策略降为明确受限的应急机制。
这一步必须在扩展大输出工具之前完成。

验收覆盖长中文会话、多批工具、早期用户约束、摘要后继续、进程重启、审批恢复和来源忘记。
程序检查工具调用配对、操作不重放、预算不重复结算、未知用量不免费、隔离与遗忘。
固定任务检查摘要前后的关键约束与事实，另行报告 judge/人工评价，不能只断言“没有超窗”。

### B：开发工具闭环

先完善文件搜索与差异查看，再实现带预览的补丁，随后交付隔离命令 job、取消和日志回读。
同步“分析/开发”模式、权限设置、审批与聊天进度。

使用临时 Git fixture 完成两条完整任务：

1. 修复一个接口校验缺陷，添加回归测试，执行测试，查看差异，准确汇报结果。
2. 生成项目文档和配置，构建失败后定位原因、修复并再次构建。

另测用户已有修改、文件哈希冲突、路径逃逸、重复审批、重复 job、中途崩溃、超时子进程、
日志过大、命令 unknown 和快照过期。不得以工具返回固定“成功”的演示代替真实执行。

### C：独立 Memory 与质量基线

完成以上主体验收后，继续 Si Memory MCP stdio 的读写闭环；它复用 Memory Service，
不依赖开发命令、会话压缩器或 Agent Loop。
随后推进 PostgreSQL 检索质量基线、Eval Lab 和真实 Langfuse 联调。

本轮不承诺一次性完成 A/B/C，也不修改现有记忆留存策略。
每个阶段都提交中文验收报告，经过针对性检查与 CI 后同步 GitHub。
